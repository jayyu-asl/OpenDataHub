# Management foundations for parcel-like offline component delivery

Research date: **2026-11-02**. Question: [Evaluate management foundations for parcel-like offline component delivery (#19)](https://github.com/jayyu-asl/OpenDataHub/issues/19). This is documentation and released-source inspection, **not an implementation, selected stack, shipping BOM, cost measurement or Certified Path**. No services were deployed and no lifecycle, security or recovery tests were executed.

## 1. Answer and decision boundary

**Bounded recommendation for the human decision: favor first-party lifecycle orchestration over mature host primitives, while reusing suitable Bigtop build recipes and upstream native operations.** Do not interpret this as “write a process supervisor” or “Ansible is the management product.” Linux service management, package installation and remote execution are reusable; the platform still owns the durable, scoped, secure operator journey. No backend language, agent transport, database, Ansible dependency or exact component version is selected here.

The reason is fit to the *combined* requirements, not the absence of Ambari functionality:

- Ambari 3.0.0 has substantial implemented Hadoop lifecycle knowledge, configuration revisions, agents, request/stage/task records, monitoring, authorization and extension mechanisms. Its **effective** BIGTOP/3.3.0 model inherits BIGTOP/3.2.0; inspecting only the leaf directories understates reuse. Management packs can version definitions separately from Ambari core. These are serious arguments for reuse. [A1–A6]
- But its inspected packaging/adapters are stack/repository/select-oriented, not an already implemented independently versioned offline component-unit contract. There is useful side-by-side installation/selection machinery in Bigtop 3.6.0; it is not a transactional activation system or an immutable release manifest. The Ambari stack and Bigtop release do not even describe the same Hive/Hadoop/Tez versions. [A7–A9, B1–B3]
- Trino, disaggregated Doris/MS/FDB/Recycler and Airflow require new management adapters in either route. Bigtop **does package Airflow** in the inspected release, but that is not an Ambari Airflow lifecycle adapter. Required ownership/adoption/offboarding, uncertain-effect reconciliation, durable-audit-before-success and independently recoverable management workflows are not established by the stock interfaces. [A10–A13, B4, T1–T3, D1–D5, P2]
- Extending Ambari therefore means adapting a second management product's stack, version, execution, identity and UI semantics as well as writing the missing component/path work. The first-party route makes that product work explicit and avoids translating every new component unit into inherited Hadoop-stack assumptions. It also forfeits Ambari's considerable ready-made management functionality. **The evidence does not establish a lower measured lifecycle cost for either route.**

Choose Ambari instead if a bounded comparison demonstrates that its existing Hadoop/UI/security/execution reuse survives the required delivery and failure contracts through maintainable extensions, with fewer invasive changes than the first-party obligations. Section 10 gives a small discriminator and falsifiers. Neither foundation resolves the accepted Doris security/recovery gaps; missing admitted mechanisms block the affected production claim, not merely an installer feature.

## 3. What extending Ambari/Bigtop actually reuses

### 3.1 Effective stack, not a directory-name survey

BIGTOP/3.3.0 `metainfo.xml` explicitly extends `3.2.0`. `StackModule.resolve` first resolves explicit service parents, then the parent stack, then linked extensions. `ServiceModule.resolveInternal` inherits missing package definitions, scripts, required services, metrics, alerts, Kerberos descriptors and components/configuration, while preserving child overrides. The two Ambari infrastructure services explicitly extend `common-services/.../3.0.0`; core Hadoop definitions are in BIGTOP/3.2.0, **not** a large unseen common-services Hadoop tree. [A1–A3]

| Effective BIGTOP/3.3.0 seam | Verified source result | Consequence for reuse |
| --- | --- | --- |
| HDFS and YARN/MAPREDUCE2 | Leaf versions `3.3.6-1`; base definitions supply NameNode/DataNode/JournalNode/ZKFC/Router/client and RM/NM/timeline/history/client roles | Real installation/configuration/start/stop/status and upgrade hooks to adapt, not a blank Hadoop adapter |
| Hive | `3.1.3-1`; base defines HMS, HS2, WebHCat, optional MySQL and clients; requires ZooKeeper/HDFS/YARN/Tez | Database/JDBC, security and execution dependencies already modeled, but not proof for Hive 4 or migrated CDP transaction state |
| Tez | Leaf `0.10.2-1`; base supplies `TEZ_CLIENT`, required YARN and Hadoop clients | Tez is a distributed application library/client path, not a daemon to make green with systemd |
| Inherited services easily missed | ALLUXIO has no 3.3.0 leaf directory and is inherited from 3.2.0; other base services include Spark/Flink/Kafka/Livy/Solr/Zeppelin/ZooKeeper | Leaf-only enumeration is wrong. Inheritance also carries unwanted assumptions into a new stack |
| New 3.3.0 services | Ranger and Ranger KMS have actual definitions/scripts | Useful integration starting points, not universal policy/encryption coverage |
| Missing required adapters in this effective tree | No Ozone, Trino, Doris, Airflow, OpenMetadata or Iceberg-specific service definition in these production resources | Needs new/adapted integrations; Iceberg libraries/maintenance need not become a fictitious daemon |

The last row is especially important counterevidence: the **3.0.0 release notes mention Ozone**, but the inspected BIGTOP parent/child/common-service/extension resources do not supply an Ozone service definition. The release-note claim must not be used to certify effective Ozone management in this stack. The same release notes acknowledge a reduced contributor base, list LDAP/timeline/DFSRouter issues and leave upgrade guidance unfinished; this is evidence for review burden, not proof the project is abandoned. [A1, A14]

Inheritance is also a maintenance constraint. Service configuration dependencies are merged; `ServiceModule` notes no current way to remove an inherited configuration dependency. Repositories and stack `upgrades` directories are **not inherited** according to the stack-inheritance contract. The inspected BIGTOP/3.2.0 and 3.3.0 production trees have **no stack `upgrades/` descriptors**. `StackDirectory.parseUpgradePacks` loads those local descriptors and logs their absence. Existing `pre_upgrade_restart` methods and a generic Upgrade API therefore do not establish an available, tested transition for this stack. New transition descriptors/checks/configuration migrations and actual path verification remain work. [A2, A4, A9]

### 3.2 Extensions and management packs are real, but are definitions

An extension version can be linked to a compatible stack, making its services available as normal stack services. The documented extension-level model excludes top-level repositories/hooks/configuration/upgrades; relevant alerts, Kerberos, metrics and ordering belong at service level, with service-level upgrade support. This matters when adding Trino or Doris: an extension is not a self-contained offline artifact repository plus platform recovery workflow. [A5]

The released `setupMpacks.py` accepts a local management-pack archive or downloads one, reads `mpack.json`, checks prerequisites, stages definitions and creates links into stacks/common-services/extensions. `process_stack_addon_service_definitions_artifact` maps service versions to applicable stack versions. This supports independently released adapter definitions **without requiring every change to fork Ambari core**. Hooks execute code; a pack is privileged management supply-chain input, not merely inert metadata. The website's management-pack page mixes implemented CLI behavior with historical future goals; it is not evidence that every proposed dynamic API exists. [A6]

Distinguish four versions: **management application**, **adapter/mpack definition**, **component binary**, and **Platform Distribution combination**. They can differ. A management-pack archive packages management definitions, not automatically the binaries, their native/JDK/Python closure or the legal/source materials. First-party CI/release evidence must bind all four even on the Ambari route.

### 3.3 Package, repository and version-selection seams

Ambari's inherited service metainfo asks for names such as `hadoop_${stack_version}`, `hive_${stack_version}` and `tez_${stack_version}`. `Script.install_packages` creates package resources; `format_package_name` uses command/repository information and can resolve available repository packages. `stack_tools.json` points to Bigtop `distro-select`/`conf-select`, and `stack_packages.json` maps roles to selection scopes. These are reusable hooks, not an opaque hard requirement to use one exact commercial format. [A7, A8]

Ambari is **not strictly limited to one undifferentiated version for all services**: version-definition manifests, PATCH/SERVICE repository types, per-service desired repository versions and partial orchestration scopes exist. `ServiceResourceProvider` requires STANDARD repositories during initial cluster provisioning. Accommodating independent component units must be evaluated against these real constraints; declaring independent units “impossible in Ambari” would be unsupported. Conversely, these facilities do not themselves prove arbitrary independent version mixing. [A8]

Bigtop 3.6.0 supplies build dependency ordering, per-component upstream versions and RPM recipes with stack-version suffixes/versioned `parent_dir` paths. Its BOM pins Hadoop `3.4.3`, Hive `4.0.1`, Tez `0.10.5` and Airflow `2.11.0`, unlike the inspected Ambari effective versions. Changing the repository URL to Bigtop 3.6.0 would not update the inherited Hive configuration/schema/security/upgrade logic or certify the new set. [B1, B2]

`distro-select` has a real role-to-directory map and changes `/usr/bigtop/current/...` links to a selected version's `usr/lib` tree. It checks version-directory existence, then removes/recreates symlinks, including locked contexts. **This is not atomic multi-service activation, digest verification, safety preflight or a state rollback.** Component payloads can remain installed side by side, but the upstream layout is organized by stack directory; independent versions require an explicit mapping/package-layout strategy. Ambari's default repository manifest points to public Bigtop **snapshot S3** locations. Replace those with approved immutable internal inputs; do not mirror a mutable endpoint once and call its identity reproducible. [A7, B3]

## 4. Two plausible parcel-like integrations, and their ownership

The following are **integration options inferred from the inspected interfaces**, not implemented designs or newly authorized product decisions. Both can preserve the fixed monorepo and mixed source-build/repackaging choices. Bigtop can be a build-recipe input to either route; selecting it does not select Puppet or Ambari as another live controller.

### A. Ambari-centered control

1. CI emits independently identified component payloads and immutable manifests; publish dependency-complete internal repositories/payload storage plus management bootstrap packages. A reviewed wrapper RPM can install a versioned payload, or a custom service install command can stage a verified archive. Mpack installation distributes matching definitions; it **does not substitute for payload verification**.
2. Use a first-party stack/mpack to adapt service package names, layout, runtime paths, configuration and security descriptors. Map admitted unit versions to repository/VDF/service records and a specific distribution combination. Reuse distro/conf-select only where its semantics fit; otherwise a service-owned selector must also report actual installed/running versions correctly to Ambari.
3. Add explicit staging and activation commands with independent status: downloaded ≠ verified ≠ staged ≠ selected ≠ running ≠ validated. Stop/drain native workloads before a supported activation, maintain previous payloads under retention policy, and preserve external state/configuration separately. Do not equate Ambari `INSTALL`, a symlink switch or a package's post-install script with the complete activation contract.
4. Supply transition-specific upgrade descriptors and native validation/recovery adapters. Add unit-digest/release/ownership/evidence presentation to the product UI/API/CLI. Integrate first-party planning and ambiguous-state handling with Ambari request/task identifiers rather than building two independent schedulers allowed to mutate the same resource.

**Likely extension surface:** stack/service scripts, packages, metainfo, advisors, Kerberos/alerts, management packs and upgrade descriptors. **Possible core/UI adaptation surface requiring validation:** arbitrary delivery-unit state/version visibility, environment/scope authorization, durable audit gating, enrollment policy and uncertain-operation semantics. Bootstrap host-key safety can alternatively be addressed by a separately verified manual/preinstallation path instead of using the insecure automatic bootstrap command; not every finding necessarily demands an Ambari core fork. Exact feasibility of extension-only compliance is unresolved. [A5–A13]

### B. Bounded first-party control over host primitives

1. Reuse OS package tooling and/or versioned immutable payload directories; pin actual OS/JDK/Python/native libraries rather than assuming a tarball is runtime-complete. Reuse suitable Bigtop recipes, patches and smoke fixtures as reviewed inputs. There is no need to replace package-manager dependency transactions with a custom package manager.
2. Reuse systemd for service users/process groups, service start/stop, restart limits, cgroups and local logs; configure the native foreground launcher or correctly bounded forking/PID model per service. Use native component APIs/CLIs for distributed membership, drain, schema and recovery. No new supervisor, scheduler, storage snapshot engine or database engine is proposed.
3. Optionally use Ansible for host/package/account/configuration automation and transport, under one management owner. Separate plans/observations and durable operation identities from playbook invocations. Ansible is an executor option, not the selected persistent state/control plane. A persistent agent is likewise not selected merely because the product needs observation and reconciliation.
4. First-party management owns the same delivery-unit state progression, scoped inventory/authorization, accepted baseline/drift, operation journal, approvals, audit, observation and service adapters that the contract requires. A recoverable independent management state store and a secure trust/enrollment/credential mechanism remain necessary choices, not features obtained from systemd.

The last point is the principal risk of this recommendation. A collection of units and playbooks would be **incomplete**, not a cheap equivalent of Ambari. The comparison is between an adapted management product and a first-party management product using reusable mechanisms, not Ambari versus a shell script.

## 5. Execution: retries are not reconciliation

Ambari's request/stage/task APIs and JPA `HostRoleCommandEntity` persist useful status, timing and output. `ActionScheduler` can cancel and reschedule timed-out commands, or mark unknown/unavailable hosts failed. Agent `ActionQueue` executes commands and can retry within a duration; `CommandStatusDict` keeps unacknowledged reports in process memory and resends them. `RecoveryManager` has bounded auto-install/start/restart behavior based on component current/desired states. This is substantial reuse, **not zero execution machinery**. It is also not a demonstrated durable exactly-once effect protocol for arbitrary scripts, database migrations, remote jobs or adoption. [A10–A11]

For example, after a schema command takes effect but its reply is lost, “TIMEDOUT → retry” is not sufficient. The adapter must inspect the native schema/operation identity, actual binary/configuration generation and current owner before choosing continuation, verified safe retry or repair. Agent output files/server task rows can assist but do not by themselves prove the result of a remote side effect. A cancellation response likewise does not prove that already submitted distributed work ceased.

The same criticism applies to Ansible. Released async execution writes a job result file under `ANSIBLE_ASYNC_DIR`, polls via `async_status`, kills the process group on its timeout and can clean up the status file after completion. This is more than synchronous SSH, but not a durable multi-service operation journal. Losing an SSH response or killing a launcher cannot retract a job already submitted to YARN or a database commit. `systemd_service` explicitly documents `started`/`stopped` as idempotent and `restarted` as **always bouncing the unit**; “Ansible tasks are idempotent” is not a safe blanket retry policy. [H3–H4]

**Required on either route:** record intent/plan/target and operation identity before hazardous effects; retain attributable per-target results and evidence; classify completed/failed/unresolved/not-run steps; observe native state after ambiguity; block unsafe dependents; and fence conflicting controllers, including restored stale management instances. The precise journal/lease/agent design is deferred. This report does not propose a universal state machine or require exactly-once execution. It requires the already agreed conservative behavior when effects are unknown.

## 6. Representative lifecycle traces

These are **source-backed integration traces and missing contracts**, not executable runbooks or certified sequences. Each must bind the actual release, topology, artifacts, permissions and native recovery conditions. Installation, configuration, restart, supported change, adoption/offboarding, partial failure and recovery are separate claims.

### 6.1 HDFS → YARN → Hive/HMS → Tez

**Install/configure/restart.** Ambari's inherited DataNode and NodeManager scripts call `install_packages`, render service configuration and start/stop under the service-specific paths/users. HDFS supplies native roles including JournalNodes/ZKFC; Hive metainfo requires ZooKeeper/HDFS/YARN/Tez and client co-dependencies. HMS startup performs configuration, optional schema initialization and schema-related checks. `TezClient.install` installs packages and configures the client; its status intentionally reports a client without daemon status. [A1, A15–A17]

This is the strongest Ambari reuse case. A first-party route needs equivalent native adapter knowledge, not just units for NameNode, RM and HS2. In either route the unit closure includes relevant JDKs/native libraries, `libhdfs`/filesystem clients, JDBC drivers, Hadoop configuration and Kerberos/delegated worker credentials; RM/NM/AM/tasks and staging/recovery/history/log paths must work with outbound access denied. A selected Ozone path can require the approved auxiliary HDFS Supported Dependency. Ambari's HDFS-oriented required-service definitions must not silently dictate all future storage choices.

**Execution and health.** The inherited Tez service check submits `orderedwordcount` through Hadoop and checks an output `_SUCCESS` path; it also prepares/copies Tez libraries into HDFS. This is useful **real distributed-work** smoke code, not just a TCP probe. It does not reconcile the project's Hive queries, ACID migration, Iceberg compactor final state, authorization or mixed-workload envelope. HMS `status` uses PID checking, illustrating why host/process, service and end-to-end health must remain distinct. [A16–A17]

**Supported change.** The DataNode script includes shutdown/post-upgrade checks and selection hooks; NodeManager has pre/post-upgrade hooks. HMS `upgrade_schema` invokes native schema machinery and explicitly says it must not run for downgrade: **metastore only supports schema upgrades in this adapter**. It can obtain/copy JDBC drivers, so those paths must be made offline-complete and rights-checked. No inspected BIGTOP stack upgrade pack establishes the actual transition. Native HDFS documentation distinguishes rolling binary downgrade from state rollback, requires a prepared rollback image, bounds reversal by finalization and requires downtime for rollback. Native YARN graceful decommission supplies node/container draining behavior, not a universal application checkpoint. [A9, A15–A17, N1]

**Adoption/offboarding and failure/recovery.** Assess actual binaries/layout, HMS schema/transactions, file ownership, active workloads, security and existing manager before a controlled transfer. Do not use a normal new-install schema/format path on adopted data, or infer adoption from installing an agent. Stop conflicting management, remediate only under the approved plan, validate real Hive/Tez/data/security outcomes and record partial transfer if any step fails. Offboarding hands over live configuration/accounts/certificates and operating responsibility without implicit service stop or data deletion. Retained binaries cannot reverse a finalized HDFS transition or migrated HMS/ACID state; native state recovery and compatible files/catalog/transaction/security material remain mandatory. These are first-party workflow/admission responsibilities in either route, not a delivered stock adoption/recovery guarantee. [fixed #7/#9/#10]

### 6.2 Trino as an independent query service

**Install/configure/restart.** Trino 476 supplies a server tarball, launcher and distinct node/JVM/config/catalog files, recommends a data directory outside the installation and requires stable unique node IDs across upgrades. It requires Java **24, minimum 24.0.1** in this anchor—not Ambari's management JVM or a universal platform JDK. A component unit can stage the admitted tarball plus its exact runtime/plugins and preserve identity/configuration/data separately. Ambari needs a new adapter; the first-party route needs a unit/native launcher adapter. Neither needs to reimplement the query engine. [T1]

**Supported change/drain.** The documented worker graceful-shutdown API is `PUT /v1/info/state` with `SHUTTING_DOWN`; the server implementation marks this endpoint `MANAGEMENT_WRITE`. The native worker protocol stops accepting new work after grace and waits for active tasks. It is **worker-only** guidance, not a coordinator HA or universal rolling-upgrade guarantee. Adapters must use the admitted authentication/TLS/authorization rather than the docs' illustrative HTTP URL or insecure certificate bypass, observe completion before terminating, and handle stuck queries/timeouts and the separately approved coordinator maintenance path. A process restart alone is not graceful drain. [T2–T3]

**Adoption/offboarding and recovery.** Inventory existing node identity, catalogs, plugin/runtime versions, external catalog/storage authorities, secrets and active queries; transfer one controller, preserve those materials on offboarding, and validate permitted and denied queries. A lost shutdown response calls for state/task observation, not an unconditional restart. A versioned binary and copied catalog properties do not restore mutated external tables, credentials or dependent authorities. Trino's own security overview separates client, intra-cluster and data-source security and states the default installation has no security enabled. Foundation choice does not secure these links automatically. [T1–T3]

### 6.3 Disaggregated Doris: FE + compute BE + MS/FDB + Recycler + native files

**Install/configure/restart.** The frozen 4.x host guide describes FDB first, MS with an actual FDB connection string, FE/BE in cloud mode, and either combined MS/Recycler or separate roles. The released `cloud/script/start.sh` implements `--meta-service`, `--recycler`, daemon/console/foreground paths and PID handling. A separate Recycler process is optional packaging; the **Recycler function is not optional**. Dedicated service identities and correct process-group/stop behavior must be adapted, not assumed from the sample scripts. Neither inspected Ambari stack nor Bigtop catalog supplies this complete management adapter. [D1–D2]

FDB is both a service and a native/client closure problem. Tagged `cloud/CMakeLists.txt` lists client versions `7.1.57` and `7.3.69`, defaulting to `7.1.57`, and installs additional native clients. The same release's `build_fdb.sh` defaults to `7.1.55` and a moving build-container tag; frozen family guidance says 7.1.x. **These are conflicting/partial input anchors, not permission to pick any FDB server/native/external-client mixture.** Inspect the actual artifact and pin its admitted clients, server, libraries, tools and configuration; a generic `fdbserver` package dependency is inadequate. No extra FDB version was chosen here. [D1–D3]

**Supported change.** Frozen family guidance orders MS → separately deployed Recycler → BE → FE (observers/non-master before master), calls for FE metadata backup, and distinguishes patch downgrades from unsupported minor/major downgrades. It is a useful candidate adapter contract, not exact 4.1.5 path proof. Translate its illustrative copying of binaries into staged/verified units with preserved configuration/state and actual native version/health checks. Changing a symlink cannot validate FE/MS compatibility, storage credentials, MS/FDB links or all native-file/ingestion state. FDB upgrade/replacement is a separate native operation, not implicitly covered by the Doris component sequence. [D4]

**Adoption/offboarding.** Reject or separately remediate an integrated FE/BE deployment rather than treating agent enrollment as conversion to this target. Assess instance/cloud identities, compute groups, FE metadata, FDB authority and native vault ownership/prefixes, writer and Recycler control, ingestion/source/WAL conditions and security before transfer. Offboarding must hand over all roles and dependencies coherently; leaving Recycler or an auto-starting old MS behind is not cessation of control. Separate Deployment Environments cannot share one Doris instance merely by using different compute groups. [D1; fixed #7/#10]

**Ambiguity/recovery/security.** Build directly on the accepted immutable [Doris recovery report](https://github.com/jayyu-asl/OpenDataHub/blob/d399f01813a2cd0afe6b08fa96f27210134f6a43/docs/research/doris-backup-dr.md) (**P2**). The default 4.1.5 `CloudSnapshotHandler` still throws `NotImplementedException` for submission, auto-snapshot refresh and clone; snapshot RPCs do not supply a complete recovery engine. FDB backup provides FDB consistency, not compatible FE state/native vault files. Its backup documentation says stored backups are **not encrypted at rest**, and `fdbdr switch` requires both databases. Its TLS has a separate configuration/trust contract. [D5, D7]

Both routes need native status/transaction/authority observations after ambiguity, old-writer and Recycler fencing, independent compatible recovery sets, protected historical keys, query/security validation and distinct current-target activation versus later failback. Frozen Doris TLS guidance explicitly describes a framework without a complete stock implementation for every protocol. An adapter, Ambari security wizard or systemd unit cannot manufacture the missing admitted runtime. A licensed/supportable extension or other admitted protection/recovery composition must be established before the affected production claim; this research does **not** authorize writing a custom TLS or backup engine. HDFS-vault and candidate Ozone-S3G native paths remain separately evidenced; external Iceberg queries and S3 API overlap do not certify native writes/recycling/recovery. [D6–D7, P2]

### 6.4 Airflow and Python dependency/state closure

**Actual reuse and counterevidence.** Bigtop 3.6.0 has an Airflow 2.11.0 recipe, scheduler/webserver systemd units and a source patch. The build creates a virtual environment using `--upgrade-deps` and `pip install .`; installation relocates it into `/usr/lib/airflow`. Its RPM `%post` executes `airflow db init` and recursively changes ownership of `/var/lib/airflow`. Those are actual scripts, not a proposal for a fully isolated stage. **Stock package installation can mutate state before a separately planned activation.** The units demonstrate process supervision under `airflow:airflow`, not dependency-complete lifecycle management or safe adoption. There is no corresponding Airflow adapter in the inspected Ambari production tree. [B4]

**Install/configure/restart.** Either route must freeze the Python ABI, selected providers/extras, wheel/native dependency closure, constraints contents/digests, DAG/plugin distribution and executor-specific database/broker/workers. Airflow's tagged installation guide explains separately versioned providers and release constraints, which can exceptionally be updated even on a versioned constraints branch: freeze the actual file, not just its URL. The generic Bigtop pip recipe is useful starting material but does not demonstrate those offline/pinning guarantees. Provider compatibility with Spark/Flink/Hive and OpenMetadata ingestion remains path-specific, as the accepted [service integration report](https://github.com/jayyu-asl/OpenDataHub/blob/330b934d44a14b52e0f3f4bac600c272323ee80c/docs/research/service-integration-governance.md) (**P3**) already established. [B4, F1]

**Supported change and partial failure.** Airflow 2.11's upgrade guide requires native `airflow db migrate` for custom virtualenv deployments and recommends a consistent metadata-DB backup; a failed migration may leave half-migrated state. Its “offline SQL migration” option means generating SQL, **not** air-gapped dependency closure. Keep migration outside mere payload staging, establish native schema/backup state and quiescence, then coordinate relevant scheduler/webserver/worker/triggerer roles for the selected executor and verify the actual job path. Inspect DB revision/native outcome after lost contact rather than reinstalling or blindly repeating an uncertain migration. [F2]

**Adoption/offboarding/recovery.** Preserve and transfer existing DAGs/plugins, DB authority, executor/broker/workers, connection/secrets backends and controller ownership; account creation and `%post` must not silently take over incompatible existing state. Offboarding does not delete jobs/metadata or kill running tasks without an admitted procedure. Recover the compatible metadata DB, DAG/plugin/configuration and required keys, not only the old virtualenv. Airflow Fernet protects connection/variable values, not every log/DB field/persistence boundary; its documented rotation preserves old/new keys while re-encrypting. The manager must protect and recover the actual keys and separately secure API/worker/database/broker/secret links. A job side effect outside Airflow is not rolled back by restoring its metadata DB. [F2–F3, fixed #9/#10]

## 9. Integration, patch and licensing boundaries

### What has to be maintained

- **Ambari route:** first-party stack/mpack, service scripts/templates/advisors/alerts/Kerberos and upgrade definitions; unit/repository/version translation; offline bootstrap and enrollment controls; first-party workflow/evidence/UI/CLI integration; any security/audit/execution patches. Follow upstream changes to stack merge rules, Python resource-management APIs, server schema/API, agent behavior and web UI. The source includes `StackModuleTest` and `ServiceModuleTest` fixtures useful for regression work, but their existence is not a test result for a new pack. [A2, A4]
- **First-party route:** management product/state/authorization/audit/recovery and selected transport integrations, native adapters, unit/automation definitions and release-unit lifecycle. Follow admitted OS/systemd/SSH/Ansible/package and component APIs. Keep OS-specific details behind the actual adapters rather than assume the illustrative v257 or Python versions are universal. Ansible 2.19's control package requires Python ≥3.11; control/remote interpreters, collections and native module dependencies must be included in preflight/closure. [H1–H4]
- **Both:** component/build owners track upstream binaries/source/forks/patches and transitive runtimes; release owners maintain immutable combinations, vulnerability remediation, licensing/source material and dependency-complete subsets; component owners maintain native state/upgrade/capacity/recovery knowledge and reference/security/failure fixtures. This remains work when management applications version independently. No silently replaced binary, adapter or manifest in an existing release is acceptable.

Keep build-time reuse separate from runtime controller ownership. Reusing Bigtop recipes/tests does not require two controllers; using Ambari plus Ansible for disjoint, declared host preparation can be coherent, but two engines cannot independently reconcile the same files or lifecycle. “Hybrid” must name the sole owner of each resource, operation journal and uncertain-effect decision, not defer the conflict.

### Actual licenses and activities

The inspected Ambari, Bigtop, Trino, Airflow, Doris and FDB top-level license texts are Apache-2.0. Apache-2.0 permits modification/distribution under its conditions, including appropriate notices and change attribution; third-party/binary contents still need separate inventory. This is favorable reuse evidence, **not blanket clearance** of a distribution, JDK, native library, JDBC driver or plugin. [L1, L4]

Ansible's inspected `COPYING` is GPLv3 and its `systemd_service` source header identifies GPLv3-or-later. systemd's own licensing inventory says most compiled programs/libraries are effectively LGPL-2.1-or-later, with udev/GPL and other file-level exceptions. Invoking a separately packaged CLI is a different integration activity from copying code, importing/embedding internals or linking libsystemd; it is **not an automatic legal safe harbor**. Review the actual activity/combination. Do not copy GPL Ansible module code into an assumed Apache-only core and relabel it. Corresponding source, modifications, notices and relinking/other applicable obligations need artifact-specific fulfillment; copyleft is not categorically excluded by policy. [L2–L3; fixed #13]

For either route, a release's evidence must cover:

1. Exact shipped payloads/wrappers/packages, runtime/native clients, wheel contents/providers, drivers/plugins and management tools—not just their project labels.
2. Upstream origin, immutable source/patch mapping and build recipe or reviewed binary-repackaging record; applicable signatures/digests/trust, licenses/NOTICE and modification records. Bigtop component versions and download URLs help but do not establish the final binary-to-source/license closure.
3. Required matching source archives/build-installation materials and the **delivery-method-specific** fulfillment mechanism, including offline/physical delivery or applicable source offers. Public source alongside binary downloads may be valid where its license/delivery permits; neither “always put all build dependencies in the installer” nor “any public Git URL is enough” follows.
4. Confidential review/entitlement/exception evidence kept separate from public release material. A restricted extension or customer-provided vendor dependency stays conditional until rights and actual provenance/integration are established; a missing approved Doris TLS module cannot be assumed permissive merely because the calling framework is Apache-licensed.
5. Separate legal/provenance and technical Certified Path gates. A built RPM, successful license scan or upstream smoke result is not operational certification.

These are applications of the fixed policy, not legal advice or a selection of commercial/restricted candidates. Neither route promises offline rebuilding of all upstream toolchains; CI must still preserve the source/build materials its actual obligations require.

## 10. Decision confidence, falsifiers and smallest useful validation

### Why the recommendation is bounded

The source comparison supports a **fit judgment**: new heterogeneous adapters and first-party delivery/ownership/recovery semantics are unavoidable, and the parcel-like contract aligns more directly with explicit first-party release/operation state than with inheriting and adapting an existing Hadoop distribution model. It does **not** prove that implementing the first-party management product is less work. Ambari's already built UI/API, agent/status loop, config/Kerberos model, real Tez smoke and native Hadoop upgrade helpers are the strongest counterevidence. Rejecting that reuse on age, or treating service directories as full support, would both be mistakes.

Documentation cannot settle extension-only patchability, maintainability of a new product or real disconnected/security/recovery behavior. No benchmark, staffing number, elapsed implementation estimate, “full catalog coverage” or operational acceptance is asserted. Discovery used direct official sites, repository trees and tagged source rather than a general web-search provider; third-party management packs/vendor extensions were not exhaustively surveyed. Their existence with admissible source/license/support could change the result.

**Falsify or reverse this recommendation if:**

- A released, inspectable and admissible Ambari stack/mpack demonstrates independently versioned payload staging/activation, faithful version/config reporting, conservative ambiguous-effect handling and the required enrollment/audit/ownership semantics without a broad core fork; and representative traces reuse substantially more native logic than they replace.
- The first-party product cannot bound its missing UI/API/state/authorization/audit/transport/recovery work, or starts rebuilding process supervision, native transactions or a general automation engine. The suggested route loses its rationale then.
- Actual maintained adapters supply the missing heterogeneous paths under the exact artifact/security/licensing conditions. An existence claim needs implementation and path evidence, not just a README or marketplace entry.
- A small comparison shows inherited assumptions and required patches are localized/upstreamable while the first-party route's reconciliation/trust/state obligations dominate. Conversely, requiring parallel operation journals/controllers or pervasive version-model changes is evidence against Ambari-centered control.

### Smallest discriminating validation proposal — not executed or authorized here

Do **not** begin with the full catalog or a real Doris recovery engine. After separate approval, compare the same narrow lifecycle seam in disposable offline fixtures, with a stub executor first and real component validation only under explicit later authority:

1. **Definition/contract check:** resolve an Ambari candidate stack/mpack to an exported effective model; map two independently versioned units, one Hadoop-related and one tarball/Python-style service, to installed/staged/active/running versions and configurations. Prove that updating one unit preserves the other unit's identity and immutable release pin. Record every required extension and core/UI/DB/agent patch. In the host route, identify only the durable product contracts and native/systemd/automation calls needed for the identical trace; do not scaffold an entire management framework.
2. **Ambiguous-effect check:** inject an executor result loss *after* a simulated persistent native effect, plus controller/agent restart. Both routes must report unresolved state, inspect the effect, avoid a second destructive action and resume only under the accepted plan/authority. Add drift and a stale controller. A retry counter or eventual green status is not a pass.
3. **Stage/activation separation:** verify digest failure/missing native runtime/sudo/account conflicts block safely before effects. Confirm staging does not trigger a DB migration or running-service restart (the Bigtop Airflow `%post` is a concrete negative case). Retain previous binaries while declaring a schema rollback unsafe. Prove the operation history distinguishes these outcomes.
4. **Trust/audit/recovery gate:** use only independently trusted offline bootstrap materials; reject substituted/expired peer credentials; interrupt/exhaust the critical-audit sink and demonstrate durable evidence or refusal. Recover management from independent state/materials while data-service processes remain autonomous, then reconcile pending work and control ownership before enabling changes.

Use observed patch/integration inventory, semantic fidelity, upstream API dependence and reproducible failure evidence to choose—not invented points, costs or a stopwatch proxy for lifecycle cost. A later real-service slice should exercise HDFS/YARN/Hive/Tez distributed results and one non-Hadoop service, including configuration/restart/change, partial adoption/offboarding and native recovery prerequisites. Doris transport and coordinated FE/FDB/files recovery remain a **separate production gate on both routes**, not a discriminator that one manager can bypass. Actual numbers and Certified Path conditions belong to release/version decisions.
