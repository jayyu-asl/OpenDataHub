# Doris disaggregated topology and storage dependencies

**Research date:** 2026-11-02 (execution-environment clock). **Evidence ticket:** [Research Doris disaggregated topology and storage dependencies](https://github.com/jayyu-asl/OpenDataHub/issues/17). **Decision consumer:** [Define deployment topology and resource-scheduling boundaries](https://github.com/jayyu-asl/OpenDataHub/issues/7), under [OpenDataHub — Product Definition, Architecture, and Feature Roadmap](https://github.com/jayyu-asl/OpenDataHub/issues/1).

## Result and evidence boundary

The human-selected target is **Doris storage-compute separation on Linux hosts/VMs**, not classic integrated FE/BE and not Kubernetes. It requires **FE, compute BE, Meta Service, FoundationDB (FDB), a functioning Recycler, and remote shared storage**. Separating compute does not remove local disks, persistent metadata, shared failure domains or service-specific recovery. The principal platform route uses YARN for selected Hive/Tez, Spark and Flink work; these Doris/FDB host services are not thereby YARN applications. [D1] [D2] [C1]

**Route-changing findings:**

- Native Storage Vaults document **HDFS and S3-compatible storage**. This is different from external Iceberg catalog/storage access. Ozone's Doris guide explicitly covers external/catalog, load and export surfaces, **not native Storage Vault certification**. [D5] [D6] [D11] [D12]
- Ozone 2.2.2 documents the main S3 operations Doris uses, and tagged implementation supports ranged reads. This establishes a credible interface candidate, **not a certified Doris-native Ozone path**. Neither an external Iceberg query nor the phrase “S3 compatible” closes native writes, compaction, recycling, security or recovery. [C3] [C4] [O1] [O2]
- The disaggregated upgrade guide still requires **FE metadata backup**. Doris SQL **BACKUP/RESTORE excludes this mode**; FDB backup alone also does not restore FE state or native data files. A coordinated recovery procedure remains a certification blocker. [D7] [D9] [F2]
- Version details matter: the family deployment guide's FDB **7.1.x-only** wording is narrower than the **4.1.5 tagged build**, which packages a default 7.1.57 client and an external 7.3.69 client. Unified TLS settings introduced in 4.1.4 are a framework, **not complete stock open-source TLS for every Doris protocol**. [D2] [D10] [C2]

**Method:** **D** = upstream documentation claim; **C** = inspected tagged implementation, not executed; **I** = engineering implication. No deployment, interoperability test, benchmark, fault injection, sizing, shipping BOM or certification was performed. Research anchors are **Doris 4.1.5**, resolved to commit `917b20be83878e98f94e3ebf7efccc80346e3e50`; Doris **4.x-family website** frozen at `12cfb3bd72049510d2e81003f71149c3abbafab2`; **Ozone 2.2.2**; and **FDB 7.1.63** documentation for operational mechanisms, not a selected client/server combination. Family documentation contains later-version material: for example its peer-cache page labels that feature experimental **4.2.0**, while its compute-group overview claims it is on by default. Do not import either default into a 4.1.5 support target. [D3] [D13]

Read the root glossary at baseline `d9f8e3b`, the map Notes, ticket, existing optional-service and topology reports, and the canonical resolutions of [Define product personas, boundaries, and reference acceptance scenarios](https://github.com/jayyu-asl/OpenDataHub/issues/2#issuecomment-6567485286), [Define lakehouse data architecture and interoperability contracts](https://github.com/jayyu-asl/OpenDataHub/issues/8#issuecomment-6568627452), and [Define distribution support contracts and certified component combinations](https://github.com/jayyu-asl/OpenDataHub/issues/6#issuecomment-6569630098). Those decisions and the subsequent human topology checkpoints are fixed inputs, not reopened here. Technical findings below use primary sources rather than treating earlier reports as certification.

## 1. Host roles, state and placement

| Role | Verified responsibility and dependency | Support-target implication (**I**) |
| --- | --- | --- |
| **FE** | **D:** SQL/session entry, parsing/planning, authentication/privileges, schema and topology metadata remain in FE. Manual deployment retains Master/Follower/Observer roles, normally three voting Followers for production. The upgrade procedure explicitly preserves the local `meta_dir`. [D1] [D2] [D7] | FE is not stateless because MS exists. Preserve its metadata disks and quorum across actual failure domains; FE restart/leader election is not metadata disaster recovery. |
| **Compute BE** | **D:** BEs form compute groups sharing the same native data, with separate compute resources and local file caches. `deploy_mode=cloud` is set on FE and BE; BE registration assigns a compute group. Cache paths and `total_size` are configurable. **C:** BE also has separate spill-path/limit configuration. [D2] [D3] [D4] [C7] | Budget CPU/RAM, cache, spill, logs and network even though BE is called “stateless.” Local cache is not the authoritative copy or a backup. Losing/replacing a BE can require workload retries and cache warming. |
| **Meta Service (MS)** | **D:** Data-layer metadata, ingestion transactions, tablet/rowset versions/file lists; stateless service backed by FDB. Guide asks for at least three production MS processes and multiple FE endpoint addresses. [D1] [D2] | MS belongs to this environment's Doris data plane, not the independent OpenDataHub management plane. Process redundancy does not protect against loss of its FDB state. |
| **Recycler** | **D/C:** The same `doris_cloud` binary runs MS plus Recycler by default, or `--meta-service` and `--recycler` separately. Only the metadata-serving process is an FE/BE `meta_service_endpoint`. Recycler deletes expired files and metadata under lease/retention rules. A **separate process is optional; the recycling function is not an optional lifecycle omission**. [D2] [D8] [C1] | Combined versus separated process placement is a bounded packaging choice to certify, not a different metadata database. Recycler needs storage credentials and independent health/capacity monitoring; its failure can accumulate garbage. Fence it during recovery until metadata/files agree. |
| **FoundationDB** | **C:** Production startup selects `FdbTxnKv`; the alternative `use_mem_kv` is explicitly volatile/test-only, not an FDB-free production variant. **D:** FDB has persistent local data directories, configurable replication/locality and a separate coordinator majority. [C1] [C2] [F1] | Include FDB server/client libraries, process control, local SSD-backed state, quorum, backup/restore and upgrades as Supported Dependencies. More MS instances cannot repair a lost FDB quorum/database. |
| **Shared storage** | **D:** Vault stores native segments/index files through HDFS or object storage; durability comes from that backend, not classic three-BE tablet replication. Disaggregated upgrades do not require integrated-mode replica rebalancing. [D1] [D5] [D7] | Name the actual backend, bucket/path, replication/EC and failure domains. More compute groups do not create independent data copies or isolate storage/MS/FE failures. |

**Local state caveat (D → I):** do not generalize “stateless BE” to every ingestion acknowledgement. The Group Commit guide says `async_mode` returns after writing local WAL, before transaction commit/visibility; WAL is single-replica and disk/file loss can lose data. Its 4.1.5 replay notes do not promise recovery of incomplete records. If that mode is selected, certify its cloud-mode eligibility, WAL path/capacity, replay, drain/decommission and source replay contract; do not treat WAL as disposable cache or HTTP success as a durable/queryable native commit. No asynchronous ingestion mode is selected here. [D15]

**Placement is not sizing:** the manual guide's three-machine, double-redundancy FDB example and three-MS/three-voting-FE guidance are upstream HA reference conditions, not an assembled production design. FDB's own documentation additionally requires coordinator majority and real locality: multiple processes/VMs on one physical machine do not create physical failure independence. [D2] [F1]

**Network closure (D → I):** do not preflight only SQL 9030 and the guide's short 8030/9050/5000 list. The port plan also includes FE BDB JE 9010, RPC 9020 and HTTP 8030; BE Thrift 9060, heartbeat 9050, HTTP 8040 and BRPC 8060. Add configured MS endpoints, **all FDB server/coordinator endpoints**, and backend NameNode/DataNode or S3 gateway endpoints, plus path-specific identity/DNS/time/CA dependencies. Actual configured/advertised addresses, routing, MTU, bandwidth and firewall directions must be checked; opening every firewall is not the support contract. [D2] [D14] [F1]

Apply the human boundary to **every environment**: independent data-plane service instances/resource pools, not merely separate Doris compute groups in one shared instance. Production hosts/disks remain physically separate from nonproduction. Production storage/compute separation remains the default; certified co-location and resource-bounded nonproduction VMs do not waive correlated-failure disclosure. Same-environment co-located YARN and Doris need non-overlapping OS/service/YARN budgets plus queue/admission and mixed-load evidence. Compute groups isolate BE compute, **not the shared FE/MS/FDB/storage/network**. These are implications of the fixed decisions and upstream dependency graph, not new scheduler options. [D1] [D3]

## 2. Native Storage Vault interfaces and security

| Surface | Documented contract / implementation evidence | Boundary to certify |
| --- | --- | --- |
| **HDFS vault** | **D:** `type=hdfs`, `fs.defaultFS`, path prefix, Hadoop username and optional Kerberos authentication/principal/keytab. All FE, BE and MS nodes must access HDFS and complete authentication/connectivity checks. **C:** FE creation checks directory creation/existence/deletion; BE/recycler use HDFS clients. BE's generic HDFS writer includes `hflush` and conditional `hsync`/close handling. [D5] [D6] [C5] [C10] [C11] | Bind actual `hdfs://` authority/HA nameservice, canonical path, JNI/native library and Hadoop/JVM configuration on each role. Check permissions, secure RPC/data transfer, ticket renewal, close durability, failover and recycling. Kerberos authentication alone does not establish encrypted data transfer; this vault guide is not a complete TLS contract. |
| **S3-compatible vault** | **D:** `type=S3`, endpoint, region, bucket, root path, provider, AK/SK and path-style selection. Documented permissions: `head`, `get`, `list`, `put`, `multipartUpload`, `delete`. HTTPS is selectable by endpoint; an endpoint with no scheme defaults to HTTP. AWS Assume Role is documented specifically for AWS S3, not every private S3 service. [D5] [D6] | Pin one provider/API implementation and explicit endpoint scheme/addressing. Do not require public AWS/STS at runtime for an offline AK/SK path, or assume AWS-role integration works with Ozone. Protect and rotate service credentials; verify every role's access, not only FE SQL privileges. |
| **Actual S3 calls** | **C:** 4.1.5 BE uses HeadObject, **ranged GetObject**, PutObject, multipart create/upload/complete with ETags, ListObjectsV2 pagination and DeleteObjects. Recycler has list/delete and abort-multipart calls, plus versioning/lifecycle-check functions. FE vault creation performs write/head/list/multipart/delete probes. [C3] [C4] [C6] | Required evidence includes range-byte integrity, pagination/continuation, multipart completion/retry/abort, missing-object/error mapping, partial bulk deletion and read visibility after acknowledged writes. Creation probes are not lifecycle or recovery certification. Versioning/lifecycle helper functions are not proof those optional safeguards are available on every backend. |
| **Transport boundaries** | **C:** BE and Recycler S3 clients separately select endpoint/scheme and CA files. **D:** FDB TLS is separate and off by default, with client/server certificate and peer-verification configuration. Doris 4.1.4+ unified TLS settings provide extension points; stock providers reject enabled protocols lacking an implementation. [C8] [C12] [F3] [D10] | Test FE/JVM, BE/native and Recycler/native HTTPS trust separately, including private CA, hostname validation, expired/untrusted certs and rotation. Separately prove FE↔FE, FE↔BE, FE/BE↔MS and MS/Recycler↔FDB protection. An HTTPS vault or an `enable_tls` flag is not end-to-end TLS/mTLS evidence. No custom TLS module is selected here. |

**API type versus provider:** `CREATE STORAGE VAULT` documents two type values, `S3`/`hdfs`, and provider values `COS`, `OSS`, `S3`, `OBS`, `BOS`, `AZURE`, `GCP`. Reused `s3.*` property names do not prove identical wire protocols: the inspected Recycler has a separate Azure Blob SDK path. These cloud examples are neither selected private-deployment targets nor mandatory public runtime dependencies. [D6] [C12]

**Ownership and immutability:** the vault guide says a table's vault cannot be changed after creation (recreate/reload is the documented alternative); changing a database default affects only new tables. HDFS authority/prefix cannot be altered; the inspected S3 vault code restricts alteration to named properties, including credentials/addressing, rather than a transparent backend move. Vault `USAGE_PRIV` controls referencing/viewing a vault, not automatic delegated end-user storage authorization. Give native files dedicated ownership/prefixes: never let Iceberg maintenance or another service's cleanup delete Doris files, or let Doris Recycler manage lake files. The latter is an ownership constraint inferred from their distinct metadata authorities. [D5] [C9]

## 3. What Ozone evidence establishes—and does not

1. **External access is documented (D).** Doris' Ozone page says **4.0.4+**, through **S3 Gateway**, with `fs.ozone.support=true` and `ozone.*`/selected `s3.*` aliases. Its enumerated surfaces are Catalog, TVF, Broker Load, Export and Outfile; Iceberg Catalog explicitly lists Ozone. This is an external lake-storage integration surface, not a native Storage Vault recipe, nor proof that external table metadata/files become Doris native state. For the selected reference, external Iceberg authority remains HMS-backed HiveCatalog; native Serving Copies retain separate format, freshness, deletion and recovery contracts. [D11] [D12]
2. **Native API overlap exists (D/C), certification does not.** Ozone **2.2.2** documents Head/Get/Put, ListObjectsV2, single/bulk delete, multipart create/upload/complete/abort, and path-style/virtual-host addressing. Its object endpoint implements ranged GET responses. Its S3 Gateway is an additional stateless service over Ozone, not a replacement for OM/DataNode persistence. This overlaps Doris' native S3 calls, but the inspected Doris vault guide neither names Ozone nor documents passing `fs.ozone.support`/`ozone.*` as native vault configuration. A generic S3 vault against S3G is therefore a **candidate requiring exact configuration/client/server verification**, not a negative claim that it cannot work. [O1] [O2] [O3] [C3] [D6]
3. **Security/limitations remain real (D → I).** Secure Ozone S3 uses Signature V4 with secrets obtained through Kerberos-authenticated administration; unsecured mode accepts dummy credentials and is not security evidence. Ozone documents deviations in missing-object responses and incomplete AWS ACL/bucket-policy parity, and lists S3 bucket versioning/object locking/SSE as unsupported. These are documentation-scoped limitations, not a claim that Ozone lacks its own encryption or authorization. In particular, do not rely on the Doris Recycler guide's object-versioning recovery suggestion for this Ozone anchor. Pin S3G HTTPS configuration/trust and verify Ozone authorization and credential revocation separately from Doris SQL grants. [O1] [O3] [O4] [D8]
4. **OFS is not an HDFS vault alias (C → I).** Ozone's filesystem interfaces do not imply HDFS wire/client interchange. The Doris HDFS writer's flush/sync calls make a blind substitution especially unsafe: Ozone 2.2.2 disables filesystem hsync/hflush by default behind an experimental enhancement gate. No inspected source certifies an `ofs://`/`o3fs://` Doris native vault. Establish client packaging and the actual required semantics before offering such a path; this does not assert that every native write always invokes every generic HDFS writer branch. [C5] [O4]

**Support-target consequence:** retain HDFS-vault and Ozone-S3G-vault as **separate evidence candidates**, not two already supported options or a mandate to install both. Prefer one analytical backend only after it satisfies the selected paths. If Ozone native vault validation is absent/fails, expose that unresolved capability and explicitly scope any required HDFS coexistence; do not silently advertise Ozone-native storage based on external queries. Auxiliary HDFS allowed for Hive/Tez does not automatically certify or supply the capacity/lifecycle envelope of a Doris native vault. No transparent URI switching or replication follows.

## 4. Bootstrap, failure and recovery boundaries

- **Bootstrap (D → I):** the host guide orders FDB/shared storage → MS/(separate Recycler) → FE quorum → BE → vault/default vault. Preserve unique cluster identities, FDB connection information, FE metadata, configuration and secrets. Its public-download examples are not an offline dependency closure: pre-acquire approved Doris/MS, FDB server and matching native/external clients, Java and path-specific Hadoop/Kerberos/CA dependencies. Keep OpenDataHub management bootstrap/recovery independent of managed HDFS/Ozone/YARN as already decided. [D2] [C2]
- **Availability is layered (I):** a BE/cache loss is different from FE quorum loss, unavailable MS, FDB coordinator/replica loss, gateway outage or shared-storage metadata/data loss. Cache warmth may alter degraded behavior but cannot establish full availability or durable recovery. Multiple compute groups still share control metadata and files. Define in-flight ingestion/query retry outcomes, not merely process replacement. [D1] [D7] [F1]
- **Recovery has three state authorities (D → I):** FE SQL/control metadata, FDB data-layer/transaction metadata, and native files must agree. FDB documents point-in-time backup/restore through `fdbbackup`/`fdbrestore` plus executing `backup_agent` processes; this protects FDB, not an atomic FE+FDB+vault snapshot. Shared files alone cannot be assumed sufficient to rebuild the catalogs/transactions. The inspected sources do not supply a complete coordinated disaggregated disaster-restore recipe. Fence writers and Recycler, establish a compatible recovery point/retained files, restore through an approved sequence, and reconcile before re-enabling deletion. Numeric RPO/RTO and retention remain later path-specific gates. [D7] [D8] [D9] [F2]
- **Changes (D → I):** upstream documents rolling order **MS → separate Recycler → BE → FE (Observer, non-Master, Master)**, FE metadata backup and load retries. Mode switching is unsupported; major/minor downgrade is unsupported in that guide. These are documented procedures, not blanket no-interruption or safe rollback guarantees, and they do not upgrade FDB/shared storage automatically. The 7.1.x guide versus 7.1.57/7.3.69 client evidence must be resolved against actual artifacts before fixing the server/client pairing and upgrade path. [D7] [C2]

## 5. Concrete certification gates

These are **future acceptance evidence**, not tests run or a release BOM:

1. **Named dependency/ownership record:** bind Doris build, MS/Recycler process variant, FDB server/client pair, Java/Hadoop/native clients, backend/interface/URI, local paths and security modules to one Certified Path. Record one lifecycle/configuration owner per resource, environment and permitted Service Adoption remediation. Reject integrated-mode adoption as disaggregated management unless a separately validated migration exists.
2. **Infrastructure/offline preflight:** customer supplies hosts/VMs, disks and networking; platform verifies configured failure domains, local mounts/permissions/free-space limits, CPU/runtime/OS prerequisites, all advertised network endpoints, DNS/time/CA/identity and offline artifact closure, and blocks unmet deployment conditions. Demonstrate cold bootstrap/restart/replacement with outbound access blocked and no circular management recovery dependency.
3. **Native interface proof:** separately validate HDFS or the exact Ozone-S3G candidate across FE, BE and Recycler. Exercise range reads, large/multipart writes, listing/pagination, retry/ambiguous completion, compaction/schema-change files, deletion/garbage collection and negative/partial failures. Reconcile native rows/versions and retained files; a vault-create probe or external Iceberg SELECT is insufficient.
4. **Security proof:** verify least-privilege storage/service identities, vault/SQL permissions and raw-storage bypass boundaries; keytab/AK/SK renewal/revocation; per-role HTTPS CA/hostname rejection; FDB TLS and each Doris internal protocol actually required by the security baseline. Missing protocol implementation is a disclosed blocker, not solved by setting an unsupported flag.
5. **Application recovery proof:** inject separately scoped BE/cache/disk, FE leader/quorum, MS, Recycler, FDB node/quorum and gateway/storage faults. Demonstrate supported retries and data correctness. Restore FE+FDB+vault from compatible retained state with writers/deletion fenced, prove Recycler resumes safely, and meet declared numeric recovery targets. Do not substitute SQL BACKUP/RESTORE, object replication or FDB-only restore for this evidence.
6. **Resource/change/adoption proof:** validate cold/warm-cache mixed batch/stream/interactive loads under explicit non-overlapping host/YARN/Doris budgets and admission; shared storage/network and compaction/recycling count. Verify supported rolling upgrades and a failed intermediate step, plus two-environment targeting/isolation and admitted-service recovery. Co-location is a separately certified variation, not inherited support.

**Unresolved factual gates:** exact selected Doris/FDB package pairing; complete stock-artifact/internal-protocol security coverage; a documented and demonstrated coordinated metadata/file restore; and native Ozone-S3G lifecycle interoperability. This bounded study neither certifies nor rules out the Ozone candidate. It supplies conditions for the already chosen architecture, not a reason to revert to integrated Doris or reopen the principal route.
