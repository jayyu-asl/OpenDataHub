# Go-native durable lifecycle orchestration reference patterns

Research date: **2026-11-02**. For [Research Go-native durable lifecycle orchestration reference patterns](https://github.com/jayyu-asl/OpenDataHub/issues/20). Public released-source inspection only; no code, prototype, deployment, benchmark or operational tests.

## 1. Answer and fixed boundary

**Learn from all four references below; adopt none as the durable operation engine on this evidence.** Combine level-based observation, transactionally recorded intent/work, explicit attempt ownership and conservative external-effect reconciliation in a bounded first-party operation Module. A transition library can simplify local guards; it cannot supply durability or service safety. Library selection remains human-owned.

This extends the accepted [Management foundations for parcel-like offline component delivery](https://github.com/jayyu-asl/OpenDataHub/blob/d93b8a921dfd05ee2a26f58afcac7df728a06be9/docs/research/management-foundation-parcel-evaluation.md), not its whole-platform comparison. Fixed inputs are the [Choose the implementation stack and repository organization — packaging checkpoint](https://github.com/jayyu-asl/OpenDataHub/issues/11#issuecomment-6573754494), [Choose the implementation stack and repository organization — application/state/bootstrap checkpoint](https://github.com/jayyu-asl/OpenDataHub/issues/11#issuecomment-6575515751) and [Choose the implementation stack and repository organization — communication/security checkpoint](https://github.com/jayyu-asl/OpenDataHub/issues/11#issuecomment-6575642387): Go controller/agent/core CLI; modular monolith, optionally separate workers; **both PostgreSQL and MySQL** management backends, admitted customer DB or default platform-managed PostgreSQL; systemd; controller-first, direct first-party Go SSH installation/enrollment; agent-initiated gRPC/mTLS; management REST/OpenAPI; React/TypeScript; FreeIPA/OpenBao companions. Immutable parcel-like delivery and monorepo boundaries stand.

The canonical [Define management-plane responsibilities and lifecycle workflows](https://github.com/jayyu-asl/OpenDataHub/issues/10#issuecomment-6573412824), [Define the security, governance, and recovery baseline](https://github.com/jayyu-asl/OpenDataHub/issues/9#issuecomment-6572177820), [Define distribution support contracts and certified component combinations](https://github.com/jayyu-asl/OpenDataHub/issues/6#issuecomment-6569630098) and [Define redistribution, licensing, and source-delivery boundaries](https://github.com/jayyu-asl/OpenDataHub/issues/13#issuecomment-6569196014) remain authoritative. No Kubernetes, Raft, Redis or independent Temporal runtime is selected by studying their patterns.

## 3. What the implementations actually teach

### Reconciliation is not a command journal

controller-runtime's `processNextWorkItem` obtains a key, defers `Done`, invokes reconciliation and chooses `Forget`, rate-limited requeue or `RequeueAfter`; a terminal error suppresses that retry, not all future events. Workers avoid concurrent handling of the same key **within that controller**, not across arbitrary hosts. The reconciler reads current state rather than treating an event as a durable command. [C1]

Its optional priority queue stores keys/readiness in maps, a B-tree and channels. Controller shutdown cancels context and waits for workers; this neither persists delayed retries nor reverses an external action. Kubernetes informer startup/cache synchronization and re-observation support convergence, but the operation's durable intent must live elsewhere. The FAQ acknowledges stale cache observations. Borrow the observe/compare/act/reobserve discipline, **not automatic restoration of drift that requires operator choice**. [C2]

Manager leader election uses Kubernetes lease machinery; `LeaderElectionReleaseOnCancel` explicitly requires the binary to end immediately or it is unsafe. A leader lock is not proof that an old agent/native job stopped. There is no ready-made PostgreSQL/MySQL operation journal here. [C3]

### Durable Go tasks: River's strong transaction boundary and weak external boundary

`JobGetAvailable` selects eligible rows with `FOR UPDATE SKIP LOCKED`, then marks them running and increments attempts. Job arguments, schedule, errors and terminal status are database records. `InsertTx` couples an application update and queued intent in the **same database transaction**; `JobCompleteTx` can similarly couple completion and transactional DB work. Those management transactions do not make SSH, gRPC, a different service database or a remote native schema/job effect atomic. [R1–R2]

The scheduler promotes stored scheduled/retryable work. The rescuer requeues old running jobs or discards exhausted ones; `RescueStuckJobsAfter` explicitly warns that a still-running job can be executed again. Default retries have jitter and bounded attempts; these govern delivery, not whether repeating a native operation is safe. The completion SQL checks running state, not an external target's fencing token. Maintenance leadership has expiring DB records, but this is not service-writer ownership. [R1, R3, R6]

`Stop` drains; `StopAndCancel` cancels contexts but still waits. `JobCancel` is cooperative: a running goroutine cannot be forcibly interrupted, and a successful return can still complete after cancellation was requested. Thus cancelled delivery is not proof of no native effect. Persisted one-off schedules also differ from periodic scheduling: `NewPeriodicJob` documents approximate, **in-memory** scheduling across leader changes, not a durable calendar/missed-run guarantee. [R2, R5]

**Dialect falsifier:** `riverdatabasesql.DatabaseName()` returns `postgres`; accepting `*sql.DB` does not mean MySQL. PostgreSQL migrations/queries contain enums, JSONB/arrays, partial/GIN indexes and `pg_notify`; polling can replace notification delivery, not translate SQL. The SQLite driver calls itself early-testing/minimally field-used. No MySQL implementation appears in the inspected driver tree; a new driver would require real SQL, locking, migration and failure work, not a DSN change. [R1, R4]

### Durable workflows: Temporal's separations, without selecting its platform

The Go server separates deterministic workflow decisions from effectful activities, with SDK workers outside the server. History records decisions/results; mutable state summarizes progress; persisted transfer tasks bridge dispatch, and timer tasks resume work later. Queue checkpoints/reloading tolerate reprocessing. Importantly, the SQL path **appends history first, then transactionally updates mutable state plus tasks**, with history validity tied to committed state: it is not one magical transaction spanning everything. [T1]

`RetryActivity` checks policy, cancellation, retryability, attempts and expiry, increments the attempt and generates a retry task. Timeout handling can call it after an activity ran without a recorded completion. For task-token completion, the handler checks attempt/version against current activity state; cancellation has distinct requested/acknowledged handling. These prevent certain stale orchestration updates, **not an obsolete worker's external effect**. Even this engine cannot infer whether a remote migration committed when its result disappeared. [T2]

**Real dual-SQL evidence:** separate `mysql8` and `postgres12`/`postgres12_pgx` plugins, schema/update trees and backend persistence suites exist. Shard range IDs are checked while holding transactional row locks; PostgreSQL uses `FOR SHARE`, MySQL `LOCK IN SHARE MODE`, both use write locks. The MySQL session explicitly defaults to `READ-COMMITTED` unless overridden; both drivers begin transactions with default options. PostgreSQL isolation is not forced by that call. Consequently defaults, overrides, conflicts/deadlocks and uncertain commits need backend-specific validation. Separate migration manifests are implementation evidence, not proof that DDL is transactionally interchangeable. These plugin names are not OpenDataHub's supported-version choices. [T3–T4]

### A memory FSM is deliberately smaller

looplab/fsm keeps current state, transition maps, metadata and pending transition closures in memory. `Event` checks allowed source states; before/leave callbacks can cancel or defer, then state changes before enter/after callbacks. An enter/after callback error does not transactionally undo that state change or its effects. `SetState` bypasses callbacks. Async transition uses a context detached from parent cancellation and requires explicit completion/cancellation; it is **not a restartable task**. Mutexes protect local state, not distributed ownership. [F1]

The release includes race/error fixes and tests for cancellation, async transitions and concurrency. That supports a focused local-helper evaluation, not durable-execution claims. Keep native effects outside transition callbacks that could be mistaken for a commit protocol. [F0–F2]

## 4. Small pattern set for a first-party operation Module

These are PRD-level implications of the sources and fixed workflow contract, not approved tables, lease algorithms or protocol schemas:

1. **Separate intent, delivery and observation.** Retain approved plan/scope, attributed per-target progress and durable results independently of ephemeral queues/connections. Record work intent with related management-state changes transactionally; wakeups accelerate discovery, while persisted due work remains discoverable after restart. Agent receipts/results and reconnect acknowledgments need an explicit durability contract; resending a recorded result differs from rerunning work. A queue item is not authoritative native completion. [R1–R3, T1]
2. **Bound retries by effect semantics.** Distinguish safe retransmission, observation-only reconciliation, confirmed native failure and unresolved effect. Preserve native job/transaction/schema identities where available. After a response is lost **after** a schema migration or job submission, query native state/outcome first. Retry only when absence or safe deduplication/recovery is established; otherwise pause dependent unsafe work and expose operator repair/recovery. “Non-retryable” prevents replay but does not establish completion. [C1–C2, R3, T2; canonical workflow contract]
3. **Separate ownership from liveness.** Expired heartbeats/leases or gRPC disconnects do not establish that work stopped. Accept results only for the current authorized attempt/control owner; establish target-side exclusion/fencing where supported, otherwise require an admitted stop/ownership-transfer procedure before conflicting mutation. Do not copy Temporal shard fencing and claim it fences Hive writers or Doris Recycler. [C3, R6, T2–T3]
4. **Restart and cancel conservatively.** Restore intent, inspect actual state and reconcile pending/unknown operations before resuming changes. Treat cancellation as requested until acknowledged and observed; stop unsafe descendants, not autonomous data services merely because management vanished. Revalidate authority, drift and changed premises; preserve completed/failed/unresolved/not-run distinctions. [C2, R2–R3, T2; canonical workflow contract]
5. **Leave safety native.** systemd process success, queue completion and an FSM destination cannot certify quiescence, committed/queryable output, compatible backup sets or rollback. Component adapters still own native drain/schema/membership/recovery observations, maintenance safety, scoped confirmation and Service Adoption/Service Offboarding. Critical success also needs durable attributable audit; none of these libraries substitutes for the fixed authorization, trust, secret or audit contract.

## 5. License, counterevidence and remaining gates

Inspected top-level licenses: controller-runtime and looplab/fsm **Apache-2.0**, Temporal server **MIT**, River **MPL-2.0**. Learning mechanisms is different from copying implementations. Imports, copied/modified files and redistributed binaries need exact provenance, transitive/file-level license and notice/source review. In particular River code must not be relabelled Apache-only: MPL sections 3.1–3.3 require covered-source availability under their terms while allowing a larger work under other terms. This is not a blanket legal incompatibility or clearance. River Pro is not included in this evaluation. [L]

**Counterevidence:** River already implements substantial durable job machinery and Temporal implements far more complete workflow recovery than a first-party module would initially have. Their tests/migrations are valuable study material. Building a new general automation engine would defeat the bounded recommendation. Conversely, neither adding a PostgreSQL-only queue behind a nominal MySQL API nor copying a workflow platform's internals meets the fixed contract. Reconsider adoption only with a bounded dual-backend fit/license/maintenance assessment; do not silently select a second state service.

**Future evidence gates, not tests run here:** exercise the same operation semantics on admitted PostgreSQL and MySQL versions: atomic intent/work commits, visibility, concurrent claims/conditional updates, isolation overrides, deadlock handling, migration interruption and ambiguous commit recovery. Exercise controller/agent crash and restart, redelivery, stale/late results, clock/lease expiry and partition, cancellation races, and loss of reply after a simulated native persistent effect. Verify native observations prevent duplicate destructive action; test drift, denied scope, trust expiry and durable-audit outage/exhaustion with outbound connectivity denied. Later service-specific Certified Paths remain separate; no exactly-once external-effect, universal rollback or operational certification follows.

Source inspection cannot establish real disconnected behavior, performance, current support/security status, or a cheaper maintenance burden. Go SDK internals and upgrade determinism were not audited. Importing private engine internals or transplanting SQL would create ongoing upstream/schema compatibility ownership, not free reuse. Exact state tables, leases, protocol schemas, SDK/code-version compatibility designs and version implementation backlog remain outside this map.
