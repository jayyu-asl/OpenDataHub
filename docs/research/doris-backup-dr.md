# Research: Coordinated backup and multi-tier disaster recovery for disaggregated Doris

## Executive answer

**The inspected upstream versions supply useful component primitives, but not a verified end-to-end backup or cross-site cold/warm/hot recovery procedure for host/VM-based disaggregated Doris.** FE control metadata, MS/FDB data-layer and transaction state, native vault files, and selected ingestion/replay state must describe a compatible recovery set. SQL BACKUP/RESTORE explicitly excludes this deployment mode; FDB point-in-time recovery protects FDB, not the other authorities. Independent file copies or a replica count do not close this gap. Confidence: **high** for these documented boundaries; **medium** for the bounded absence-of-recipe finding. [D1][D2][F1]

**Cold recovery is a credible composition to investigate first**, using a validated quiescent capture and independently retained files/metadata. Warm requires prepositioned resources and continuing compatible-state synchronization. Hot additionally needs ready services, observable low-lag synchronization and safe automated cross-authority takeover. None is certified by this research; bounded nonzero RPO is permissible. The hardest unresolved problems are a supported FE/FDB capture relationship, destination file completeness versus metadata promotion, fencing all old-site writers and Recycler instances, and safe restoration of fixed vault identities/locations. [D2][D3][D4][C1][C2] These compositions are **researcher proposals**, not upstream runbooks.

A consequential source distinction: Doris 4.1.5 **does contain cluster-snapshot RPCs and metadata**, but its default FE `CloudSnapshotHandler` throws `NotImplementedException` for snapshot submission, automatic-job refresh and cloning. An extension-loading surface is not a stock supported backup implementation. Ozone 2.2.2 **does have native bucket snapshots and SnapshotDiff**, despite lacking S3 bucket versioning/object locking and documented S3 cross-region replication. Neither discovery establishes an independent coordinated Doris recovery set. [C3][C4][O1][O2]

### Fixed decision and handoff context

This research implements the evidence request in [Research coordinated backup and multi-tier disaster recovery for disaggregated Doris](https://github.com/jayyu-asl/OpenDataHub/issues/18), a native prerequisite of [Define feature releases and version-map handoff criteria](https://github.com/jayyu-asl/OpenDataHub/issues/12), under [OpenDataHub — Product Definition, Architecture, and Feature Roadmap](https://github.com/jayyu-asl/OpenDataHub/issues/1). **Product input, not implementation evidence:** customers may omit HA, ongoing backup or DR; production security remains mandatory. The product must ultimately offer genuine end-to-end cold, warm and hot Certified Paths, with per-path coverage rather than every combination supporting every tier. A selected but unproven tier cannot be advertised. Hot does not require active-active or zero loss. Historical backup and site-loss protection remain separate claims. No numerical SLO or shipping BOM is selected here.

### Compatibility invariant—not a global snapshot claim

**Researcher interpretation:** a usable recovery manifest must bind an FE recovery boundary, a specific restorable FDB state/version, and a retained-file set that is complete for the metadata references and visibility state at those boundaries. It must also bind relevant source/progress/WAL state and the security dependencies needed to use them. A timestamp common to several copies does not prove those relationships. [D2][D3][F1][C4]

For an online composition, the standby may receive metadata referencing objects that have not yet arrived, or an older metadata point may reference files already removed by replication/Recycler. Therefore **promotion must be gated on a validated compatible recovery set**, not independently sampled “lag looks small” metrics. A retention window must cover the oldest promised metadata point, copy/backup lag, retries and recovery duration under measured conditions; setting a retention knob does not pin files to an FDB backup version. No inspected source establishes a global FE+FDB+storage transaction or snapshot. **Interpretation; high for the hazard, medium for any proposed remedy.**

## 4. Coordinated capture, fencing and safe restart

The following is a **candidate validation design**, not a released upstream procedure. Controlled DDL/write/maintenance outages are allowed by the fixed product decision. The first release claim must not depend on assuming that arbitrary online copies work.

### 4.1 Candidate planned capture boundary

1. **Declare scope and authority.** Name all tables/vaults/instances and shared dependencies. Decide the selected load acknowledgement contract and recovery unit; do not promise global multi-table/service atomicity. Record which source/connector state is part of the unit.
2. **Fence new mutations and autonomous work.** Block ingress/DDL and producers; stop or drain scheduled load coordinators, compaction/schema changes, async WAL commits and maintenance that can change metadata/files. A load-balancer switch alone does not fence direct clients, queued jobs, old FEs/BEs, MS operations or storage credentials.
3. **Prove Recycler exclusion and retention before capture.** Tagged `enable_recycler=false` is consulted by scheduling and before queued work is instantiated; it is **not evidence of an acknowledged drain barrier for already executing deletion**. Blacklist/whitelist are filters, not a global checkpoint. Stop/fence every relevant deletion actor and verify in-flight deletion has ceased; the exact mechanism is a validation gap. Combined MS/Recycler packaging matters: stopping one combined process also stops metadata service. [C1][C2][P1]
4. **Reach a documented recoverable stopped/quiescent state.** Resolve committed/prepared/aborted/ambiguous loads, WAL and source progress; capture FE through a supported exact-build method and FDB through its supported tool while MS clients remain fenced. Preserve storage references before GC can remove them. Sequential captures are only acceptable after experiments prove the relevant state stopped changing; no global atomic snapshot is inferred. [D2][D6][F1]
5. **Capture and independently preserve the files.** Use a backend-appropriate stable snapshot/generation or a complete verified copy. Keep the primary retained generation until offsite completion and integrity checks, not only until a job launches. Publish a manifest only once FE/FDB/files/source/key materials form a compatible set and the destination is independently usable. [H1–H3][O1]
6. **Resume only through an admitted ordering.** Source GC may resume after immutable recovery materials no longer depend on mutable primary files and retention covers remaining jobs. Fail a partial capture visibly; never label a mismatched set successful. This is a proposed management contract, not an upstream API.

### 4.2 Why leases, lag and deletion are hazardous

- **Leases are not cross-clone fencing.** A restored second FDB can contain an independent version of the same lease and instance IDs. The two sites can then each consider their own Recycler/writer legitimate. Fence network/storage credentials, old services and restart automation using an authority outside the failed site's state before promoting. The owning metadata lease protects concurrent recycling in its own authority only. [D3][C2] **Interpretation; high.**
- **Retaining files is not retaining visibility.** FDB logs establish FDB point-in-time consistency; HDFS/Ozone snapshots retain filesystem/bucket images. Neither alone defines FE schema/journal alignment or transaction/source progression. Source compaction/drop and destination delete propagation must not erase the set needed by any advertised recovery point. [F1][H1][O1][C4] **Interpretation; high.**
- **Readers may not be mutation-free.** Do not assume a running standby MS can safely query an FDB being restored or held as a locked DR destination. The FDB restore warning explicitly excludes client access; tagged cloud configuration also includes lazy-transaction advancement during reads. Standby queryability and maintenance suppression need dedicated proof, not a “read-only” label. [F1][C1] **Fact plus interpretation; high.**
- **Retention defaults conflict.** The frozen 4.x Recycler guide lists `compacted_rowset_retention_seconds=1800`; the 4.1.5 tagged configuration says `10800`. Blacklist comments also say it is effective only when whitelist is empty. Do not copy family tuning defaults into a release safety argument. Record actual effective settings and validate file survival across compaction, drop and backup lag. [D3][C1] **Fact/direct; high.**

### 4.3 Candidate restoration and takeover sequencing

**Proposed dependency partial order, not an operational runbook:** establish independent bootstrap/artifacts/identity/keys and exclusive recovery authority → prepare isolated target storage and FDB with all MS/Recycler clients fenced → restore and verify the selected native-file generation and FDB target version → restore FE through its exact-build admitted procedure and validate its relationship to FDB → introduce MS without an active Recycler and controlled FE/BE access only after FDB restore is complete → reconcile transactions, sources and effective security → validate queries/results → enable authorized writers → re-enable deletion last after a dedicated GC safety check. Storage and FDB restoration may be parallel if clients remain isolated; neither can be exposed as ready before the complete compatibility check. [F1][D2–D6] **Candidate; feasibility unproven.**

All old and restored coordinators, auto-start units, load jobs and Recycler instances must remain fenced until their roles are explicitly assigned. Restoring FE/FDB may restore obsolete privileges/credentials or jobs; reconcile currently approved revocations/policy without claiming that historical data restore restores the right current security state. Ambiguous source replay must be surfaced, not silently counted as zero loss.

## 6. Storage-specific evidence and limits

### HDFS vault route

**Documented native interface:** Doris lists HDFS vault configuration and Kerberos options; HDFS authority/path restrictions make transparent recovery relocation a gap, not an assumed property. All participating Doris roles need valid backend access. [D4][D5] **Fact/direct; high.**

**HDFS 3.4.2 primitives:** snapshots are read-only point-in-time filesystem views and do not copy blocks. They can pin files against later deletion, but a snapshot on destroyed NameNode/DataNode infrastructure is not an offsite backup. DistCp recommends source/destination listing cross-checks, warns about changing source files, and documents snapshot-diff conditions: both source and target must be `DistributedFileSystem`, the target must match the starting generation and must not have subsequent mutations. Diff applies creates/renames/deletes and does not automatically create the final target snapshot. [H1][H2] **Fact/direct; high.**

**Interpretation:** dedicate destination ownership and retain independent historical generations; do not point an active standby Recycler at a DistCp synchronization target and invalidate its no-mutations assumptions. DistCp `-atomic` concerns target publication through rename, not atomic FE/FDB/storage capture. Do not confuse HDFS HA/replication within a site with a second recoverable HDFS site.

**Encrypted copy:** HDFS documents raw encrypted copying through `/.reserved/raw/` with encryption xattrs preserved (`-px`); those attributes carry information needed for decryption. Normal copy into encrypted destinations may re-encrypt and change filesystem checksums. Historical KMS key versions and backing key material remain separately necessary. Preserving ciphertext/xattrs does not itself back up the KMS. [H3] **Fact/direct; high.** Validate exact copy mode, source/destination authorization and independent integrity verification; a skipped checksum is not an integrity proof.

### Candidate Ozone S3 Gateway native-vault route

**Inherited boundary:** the earlier topology research finds S3-call overlap but no native Doris Ozone-vault certification; the documented Doris Ozone integration concerns external/catalog/load/export surfaces. This report does not re-certify interface compatibility from those pages. [P1]

**Important limitation:** Ozone 2.2.2 S3 documentation lists bucket versioning, object locking and S3 server-side encryption as unsupported, and lists lifecycle configuration and cross-region replication as roadmap work. Internal encrypted buckets are a different facility. Therefore do not rely on AWS versioning/CRR/lifecycle/Object Lock semantics or the Doris Recycler guide's object-versioning recovery suggestion for this candidate. This is documentation-scoped evidence, not a claim that Ozone lacks all replication/encryption/retention. [O2][D3] **Fact/direct; high.**

**Distinct useful primitive:** Ozone 2.2.2 native bucket snapshots are consistent read-only bucket images; blocks are not duplicated and remain while live/snapshot references exist. Snapshot administration uses Ozone RPC/shell/filesystem/Java APIs, not S3 or s3a; snapshot data can be read through the `.snapshot` path on S3. Restore is a copy process, not automatic rollback; snapshots do not version bucket metadata such as ACLs/quotas. Native SnapshotDiff and DistCp are described for replication/DR. [O1] **Fact/direct; high.** These supply a **candidate** way to pin/copy Doris files below the S3 interface, provided exact native-vault behavior and remote copies are demonstrated. They do not prove a global metadata cut or independent site survival.

**Security/state dependencies:** secure Ozone S3 uses Signature V4 with Kerberos-authenticated secret administration; the secret store defaults to OM RocksDB and an external secret provider is an option. Ozone TDE uses a KMS/KeyProvider. [O3][O4] **Fact/direct; high.** Thus independently copied objects do not automatically copy usable identities, OM namespace/security state, S3 credentials, bucket policies/ACLs or keys. A full storage-service recovery plan must account for OM/SCM/DataNode state and gateway/configuration dependencies; exact cluster-level capture/rebuild of those roles remains outside the verified recipe in this bounded report. An alternative is verified logical restore into a fresh independent secure Ozone cluster, but vault address/path portability remains a Doris gap.

**Cross-interface caution:** do not apply HDFS-only DistCp snapshot-diff assumptions, atomic rename, preserved ACL/xattr semantics or S3 versioning to Ozone by analogy. The exact Ozone-aware client, layout, snapshot access, object copying, pagination/integrity and deletion behavior must be admitted together. HDFS vault and Ozone-S3G vault are separate candidate paths with separate evidence requirements.

### External Iceberg is a separate recovery contract

Querying Iceberg from Doris does not move its catalog authority, metadata/data/delete files, encryption keys or streaming checkpoints into native Doris FDB/vault state. An independently protected Iceberg source may support rebuilding a native Serving Copy only with tested transformation/replay, source retention, correctness and RPO/RTO. External-query recovery requires its own compatible catalog/files/security path, and does not certify native vault recovery or any Doris DR tier. **Fixed product boundary and researcher interpretation**, consistent with [P1].

## 7. Security and independent offline-site prerequisites

These are release admission gates under the fixed production baseline, not a claim that defaults satisfy them.

- **Close every link.** Verify authenticated/encrypted FE↔FE, FE↔BE, FE/BE↔MS, MS/Recycler↔FDB, all backend clients/gateways, backup agents/repositories and management/identity links. The Doris TLS framework page introduces extension points from 4.1.4 and warns stock providers reject enabled protocols without an implementation. FDB TLS is separately configured; its backup docs require appropriate source/target and agent TLS options for DR. An HTTPS vault endpoint alone is not end-to-end transport proof. [D7][F1][F3] **Fact/direct; high.**
- **Encrypt all sensitive persisted boundaries.** FE metadata, FDB state, local WAL/cache/spill/logs as applicable, configs, backup manifests/materials and audit need demonstrated coverage. HDFS/Ozone TDE applies to its certified files/buckets, not automatically FE/FDB/local state. Keep historical keys under independent protected recovery access rather than bundle plaintext keys with backups. [H3][O4] **Interpretation plus product requirement.**
- **Separate privileges.** Limit ordinary recovery operators, data access, policy/audit and key administration; use distinct least-privilege storage/service identities and trace initiating/effective Platform Identity. Storage-superuser credentials must not become arbitrary-job bypasses. Native Doris SQL/vault grants do not prove raw-storage enforcement. [D4][D5] **Interpretation plus product requirement.**
- **Restore security intentionally.** Restore enough identity/policy to bootstrap safely but reconcile current revocations, retired writers and key policy before reopening. Validate expired certificates/keytabs, revoked S3 credentials, missing historical keys, denied raw-storage access and audit durability under outage. A restored old credential working is not necessarily success.
- **Survive independent primary loss.** Retain manifests, numeric FDB recovery versions, compatible binaries/native clients, package integrity metadata, OS/runtime dependencies, configs and protected secrets at a site/repository that survives the declared fault. FDB timestamp-to-version restore lookup needs the original cluster; version-target restore avoids that particular dependency. [F1] Test with original FE/FDB/storage/KMS/management endpoints unreachable and public outbound access denied.
- **Avoid circular bootstrap.** Management/repository/key/identity recovery must not depend solely on managed HDFS/Ozone/YARN that it must rebuild. Provide or explicitly assign independent DNS/time, KDC/directory, CA, policy, KMS/secret store and audit recovery. Ozone's optional external secret provider, if selected, adds another independently recoverable dependency. [O3] Dependency existence is not availability evidence.
- **Declare scope of resilience selection.** A Customer Deployment omitting ongoing backup or DR may still be production-secure, but must display actual protection and risks. An operation needing a consistent rollback point retains that prerequisite. Never substitute unverified replication for a selected managed backup/DR contract.

## 8. Proposed version-map evidence and fault-validation checklist

**No tests were executed.** These are evidence requests for [Define feature releases and version-map handoff criteria](https://github.com/jayyu-asl/OpenDataHub/issues/12), not implementation instructions or numerical commitments.

1. **Artifact and support record:** pin FE/BE/MS/Recycler builds and packaging, FDB server/native/external clients and tools, Hadoop/Ozone/gateway/client versions and layout, Java/native dependencies, security providers, all vault paths and failure domains. Record which documented claims are family-only and resolve actual effective defaults. Resolve FDB pairing and FE capture/restore support before admission.
2. **Recovery-manifest contract:** identify FE image/journal/identity boundary, FDB version/ranges and backup restorability, native-file generation with integrity/completeness checks, source/WAL/progress boundaries, schema/format versions, key IDs, config/policy reconciliation requirements, repository independence and fenced actors. Failure to acquire any mandatory material must leave an explicitly incomplete job, not publish a recovery point.
3. **Capture correctness under mutation:** exercise DDL/drop/truncate, updates/deletes and unique-key/delete-bitmap behavior, schema change, compaction/packed-file references if enabled, transaction prepare/commit/abort and lazy commit, parallel ingestion and ambiguous responses. Test quiescence failure rather than assume stop acknowledgement equals drain. Demonstrate FE/FDB visibility and all file references after restore.
4. **Recycler/GC safety:** capture while GC is active, toggle controls with in-flight work, kill/restart a Recycler, exercise combined/separate packaging and expired leases, and deliberately restore old metadata whose files would otherwise expire. Hold retention through failed/offline copy and resumption. Verify no deletion before an acknowledged barrier, no orphan deletion of live recovery files and safe cleanup after promotion.
5. **Component loss and negative materials:** separately lose FE metadata/quorum, MS nodes, FDB storage/coordinator quorum, BE cache/WAL disks, HDFS NameNode/DataNodes or Ozone metadata/data/gateway nodes. Reject mismatched FE/FDB versions, missing files/logs, partial multipart/copy results, corrupt backups, incorrect keyspaces and missing/unauthorized historical keys. Do not score process startup as recovered data.
6. **Ingestion and replay:** cover acknowledged WAL-only events where supported, committed-but-response-lost events, connector/source outage, source offset ahead/behind restored data, retention expiry and checkpoint recovery. Count lost/replayed/duplicate events and validate labels/deduplication behavior across restore; preserve ordering/sequence semantics where claimed.
7. **Independent cold-site drill:** remove all primary-site dependencies and block outbound internet; restore from retained materials and independently recoverable identity/keys. Demonstrate primary-independent FDB version selection, vault namespace/address handling, artifact availability and capacity. Validate rows/query results, schema, transaction visibility, deletes, permissions and durable audit.
8. **Warm readiness and takeover:** prove resources/services are prepositioned before failure; interrupt synchronization midway, during source deletion and at metadata-ahead-of-files boundaries. Promote only a known compatible set. Exercise planned switch with both sites alive and unplanned permanent site loss separately. Record synchronization age/completeness, not just transfer success.
9. **Hot readiness and fencing:** inject asymmetric partitions, delayed traffic, false failure detection, old coordinators/Recycler restarted by automation and dual-site storage credential access. Prove exclusive authority or refused writes. Test automatic compatible-state selection, full dependency readiness, endpoint routing and deferred Recycler activation. A single FDB automatic failover is insufficient acceptance evidence.
10. **Failback and security drift:** restore old-site network/disks with stale services intact; prevent resurrection. Reseed from the current authority, reconcile policy/key rotation and source progress, then reverse roles under a tested procedure. Demonstrate that unsupported divergent histories are quarantined rather than silently merged or overwritten.
11. **Measured publication record:** for each exact Certified Path/tier, choose and demonstrate later the numeric backup retention/window, source retention, lag/RPO, RTO, detection/fencing, cache/credential/revocation, audit buffering and degraded-load bounds. Declare measurement clocks/endpoints, fault envelope, committed/acknowledged boundary, load/hardware and exclusions. Publish separate history/HA/site-loss results; do not inherit one from another.

## 9. Contradictions, unsupported claims and unresolved questions

### Contradictions / traps retained explicitly

- **Recycler defaults:** 4.x family guide says 1800 seconds for compacted-rowset retention; 4.1.5 tagged configuration says 10800. Source/default scope must be pinned rather than silently selecting one. [D3][C1]
- **Snapshot terminology versus support:** tagged cluster-snapshot RPCs coexist with unimplemented default FE snapshot operations and the SQL backup exclusion. These are different surfaces, not evidence that the exclusion is obsolete. An admitted extension could change the support boundary, but none was established here. [D1][C3][C4]
- **Ozone snapshots versus S3 versioning:** native bucket snapshots exist while S3 versioning/locking/CRR claims remain unsupported/roadmap in the tagged docs. This is an interface distinction, not a contradiction to resolve by claiming either universal support or no recovery primitive. [O1][O2]
- **FDB regional automatic failover versus `fdbdr switch`:** one is a single-cluster regional mechanism with its own topology/fault conditions; the other is database-to-database DR direction reversal requiring both databases. Neither is whole-Doris coordinated promotion. [F1][F2]
- **Client/server version evidence:** the inherited topology report identifies a family-guidance/tagged-build FDB version discrepancy. It remains unresolved; these research anchors do not select a shipping combination. [P1]

### Highest-impact missing evidence

1. What exact supported FE backup/restore method, journal boundary and stopped/quiescent protocol establishes compatibility with FDB? How are cluster IDs, node identities and new-site endpoint changes handled without unsupported metadata edits?
2. Does an admitted released stock artifact supply a complete cluster-snapshot implementation beyond the inspected default handler? If an extension is required, where are its tagged source, license/support, security, independent-file-copy and recovery contracts? Mere RPC existence is insufficient.
3. How can a managed adapter obtain an acknowledged writer/maintenance/Recycler drain barrier, including already executing file deletion, combined MS packaging and automatic restart? What fences remain effective across cloned FDB histories and partitions?
4. How can a standby select and activate a compatible FE/FDB/file generation after permanent source loss? Is old-generation rollback possible when FDB DR has advanced past the available FE/files, and how is destination FDB activation safely performed with the exact admitted tools?
5. Which vault identity/address-preservation or relocation mechanisms are supported at a second site, particularly HDFS authority/prefix immutability? How is failback reseeding validated without mixing divergent histories?
6. Does the exact native Ozone-S3G vault pass lifecycle, security, compaction/delete, copy/snapshot and recovery tests? What Ozone-aware cross-site snapshot/copy and independent cluster-rebuild procedure is admitted? S3 API overlap and external Iceberg queries cannot answer this.
7. Which ingestion modes and connector combinations are eligible in disaggregated mode, and what source/WAL/checkpoint/label retention makes their acknowledged/committed recovery contract truthful?
8. Can hot standby keep all authorities and independent security/audit dependencies ready with safe automated promotion? No end-to-end released recipe or experiment was established here. Resolve this separately rather than presenting cold restore as completion of the long-term DR requirement.

**Residual risk:** this is bounded source research with unavailable search-backed discovery, not proof of upstream impossibility. No real combination, procedure or tier is certified. The most useful next research is an owning-source/upstream clarification of exact FE/FDB capture and snapshot-extension support, followed by design of the smallest quiescent compatible-set experiment and native-vault address/GC checks. Warm/hot design should build on that evidence, not presume it.
