# Offline distribution and lifecycle-management foundations

Research date: **2026-10-31** (`date -I` in the research environment). Scope: [planning map #1](https://github.com/jayyu-asl/OpenDataHub/issues/1), [research ticket #5](https://github.com/jayyu-asl/OpenDataHub/issues/5). The ticket was assigned to `jayyu-asl`, labelled `wayfinder:research`, and its context comment authorized this isolated report.

## Finding and evidence boundary

Maintained reusable foundations exist, but none of the examined sources establishes complete offline lifecycle coverage for OpenDataHub's catalog. Ambari merits evaluation rather than dismissal as abandoned; Helm/GitOps are not substitutes for service-specific operational knowledge. Repositories solve artifact transport/storage, not dependency completeness or certification.

This is **documentation/source research, not a tested compatibility matrix**. No software was deployed, benchmarked, or operationally verified. Tagged manifests and versioned documentation support the statements below; rolling documentation is explicitly identified. Release markers establish ongoing publication, not maintenance SLAs. Recommendations are planning implications, not selected product policy or implementation technologies. Customer deployments may select capabilities; the long-term named catalog remains required, explicit alternatives remain undecided, and only certified combinations may be promised.

## Separate three independent concerns

1. **Management-platform runtime:** where its API/UI, database, agents, controllers, and artifact services run. Ansible has a control node and remotely managed nodes; Argo CD/Flux use Kubernetes controllers. Neither determines where every managed service must run. [S1, S5, S6]
2. **Service deployment:** OS packages/system services and host automation versus Kubernetes manifests, Helm releases, and operators. An operator adds application-specific reconciliation beyond Kubernetes primitives; its existence does not establish implemented backup or upgrade behavior. [S2–S4]
3. **Engine scheduling:** YARN's ResourceManager/NodeManagers/ApplicationMasters allocate and execute application resources; Kubernetes' scheduler places Pods on nodes. These are not distribution installers. Management hosted on Kubernetes does not itself mean engines use Kubernetes; conversely, installing YARN services does not select the management runtime. Such compositions require separate validation, not an assumed support promise. [S7]

### Existing management-platform reuse is conditional

Ambari 3.0.0 is concrete reuse evidence, including service/configuration/monitoring improvements, but not a full-catalog guarantee. Its tagged stack contains HDFS, YARN, Hive, Kafka, Spark, Flink, Ranger and Ranger KMS service directories. That directory list is not the whole inherited/effective service model, nor evidence that all required OpenDataHub services are supported. Release notes mentioning Ozone must not be generalized into every stack/version combination. They also list known Timeline Service, LDAP and DFSRouter issues; containerization improvements are **roadmap**, not delivered universal support. [S2, S3]

A future reuse assessment should compare effective service definitions, configuration/version models, security posture, supported OS/JDK/database combinations, extension cost and ownership of gaps. Neither “reuse everything” nor “rewrite everything” follows from these sources.

## Disconnected delivery is dependency closure, not image copying

Kubespray's explicit inventory shows why an offline bundle needs multiple artifact classes. Its tagged offline guide even retains older Cilium/container examples; examples are not a release support matrix. Harbor bootstraps its own images, while Flux bootstrap presupposes a cluster, internal registry, Git access and credentials. **Implication:** plan a recoverable bootstrap path that does not require the target platform to host its own initially unavailable dependencies. [S1, S6, S8]

A release acceptance inventory should distinguish installation from rebuilding, then cover:

- OS/architecture-specific RPM/DEB packages and metadata; binaries, JDK/Python and native libraries; container manifests/layers for supported architectures.
- Chart dependencies, CRDs/webhooks, operators and their operand/init/hook images; Ansible collections and Python wheels; application plugins/connectors and any runtime downloads.
- If rebuilding is promised: source archives, patches, build tools and transitive Maven/Gradle/npm/Python dependencies, separately from installed binaries.
- Private DNS/time, CA trust and certificate renewal, identity endpoints, credentials, licenses/notices and offline operating documentation. These are proposed completeness checks, not claims that one examined tool supplies them all.

Artifact provenance needs immutable digests, upstream source/version/patch records, checksums, signatures and verification trust material. Bigtop publishes PGP/checksum verification; Cosign documents local image/public-key verification and bundles, but rolling documentation also labels evolving bundle features. Exact signer identity, trust-root distribution, signature/referrer preservation and disconnected verification must be tested for chosen releases. A checksum alone is not signer authentication. [S2, S10]

Scanning is another dependency chain. Trivy **0.76.1** documents vulnerability/Java databases, checks bundles, VEX and possible remote Maven/module access; `--offline-scan` suppresses remote Java lookups, not every network dependency. Version checking and telemetry have separate disable flags. Harbor's 2.14 “offline vulnerability import” page still describes **Clair**, despite its removal as the default scanner: do not copy it as a Trivy procedure. Database freshness and reduced offline findings need explicit acceptance criteria. [S11]

## Licensing, configuration and secrets

Historical licensing is unsafe evidence. The inspected Ambari, Kubespray, Helm, Argo CD, Flux, Harbor and Velero source releases carry Apache-2.0 licenses. Ansible's inspected license is GPLv3; OpenTofu's is MPL-2.0. Current inspected Terraform **1.17.1** and Vault **2.2.1** licenses are **Business Source License 1.1**, with production-use restrictions relevant to paid hosted/embedded competitive offerings and per-version change dates. They must not be presumed unrestricted open-source foundations simply because earlier versions were MPL. This report makes no legal determination that OpenDataHub is a competitive offering. [S12]

Grafana **13.3.0** and Loki **3.7.9** source licenses are AGPLv3, not their historical Apache license; Alloy's current source license is Apache-2.0. Redistribution/modification, required source availability, enterprise binaries and each plugin/dependency need artifact-specific review. A component license does not license every bundled artifact. [S12]

Configuration needs versioned schemas/defaults, environment overlays, drift ownership, validation and redaction. Avoid simultaneous writers for a resource: GitOps, operators, host automation and emergency edits need explicit boundaries. Ansible Vault protects **at rest**, not decrypted execution/logs; Kubespray warns that verbose download logging can expose repository credentials. Kubernetes Secrets are unencrypted in etcd by default and need encryption-at-rest and least privilege. Argo CD 3.5.6 recommends destination-cluster secret management; manifest-generation injection can cache plaintext secrets in Redis. An external secret provider is useful only if reachable inside the disconnected environment. [S1, S5, S14]

## Upgrades, rollback and recovery are service-specific

A distribution version must bind its OS/architecture/runtime, management software, Kubernetes or YARN, package/chart/operator versions and upgrade paths. Kubernetes' current **1.37** upgrade guide forbids skipping minor versions and separates CNI upgrades; these are not guarantees for every application. Helm hooks can run migrations, but release rollback cannot be assumed to reverse external side effects or data/schema changes. Git reversion changes desired configuration, not historical data. [S4, S5, S15]

**Planning implication:** describe each supported transition by preflight, quiescence/checkpoint requirements, ordered actions, health gates and failure recovery. Mark downgrade/rollback as conditional or unsupported where upstream cannot establish it; forward repair or restore may be necessary. Do not promise universal rollback.

Recovery must include the management database/configuration, Git and registry state, credentials/keys/PKI, Kubernetes control-plane recovery where applicable, plus component-native data/metadata recovery procedures. Argo's export/import protects its management data, not application data. Velero hooks can support consistency workflows; its filesystem backup reads a live filesystem rather than a single point in time, requires root/possibly privileged node agents, and excludes `hostPath` volumes. Storage/snapshot support and object-store access need validation. Snapshot existence is not proof of application-consistent recovery. [S5, S13, S15]

## Observability and diagnostics

Observed release markers include Prometheus **3.15.1**, Grafana **13.3.0** and Loki **3.7.9**; this is not a certified trio. Prometheus scrapes instrumented targets/exporters, evaluates rules, and uses Alertmanager for alert handling; Grafana visualizes the results. Exporter coverage and offline alert destinations still need definition. Prometheus local storage is neither clustered nor replicated, recommends snapshots for backup, and does not support NFS. Metrics collection therefore does not alone establish monitoring durability. Grafana documents offline plugin ZIP installation; mirror plugins and provision dashboards/datasources instead of assuming startup downloads. [S16, S17]

Loki 3.7.9 documents the need for an authentication/tenant-routing layer; native mTLS authenticates transport but does not assign `X-Scope-OrgID`. Its `auth_enabled` setting is not sufficient end-user authentication. Promtail is **EOL since 2026-03-02**; current upstream guidance names Alloy or another supported client, so an old Prometheus/Grafana/Loki/Promtail recipe is not a maintained baseline. Collection choice, log retention/storage, cardinality, alert routing, identity and resource costs remain certification questions, not a stack selection. [S17]

Diagnostics should work without internet or mandatory vendor upload: installation inventories, dependency-resolution failures, health checks, service/controller logs, metrics/rules, configuration revisions and backup/restore results. Kubernetes documents `cluster-info dump` including pod logs; Velero exposes hook outcomes. **Proposed safeguard:** redact and access-control support bundles before any export; logs/manifests may disclose secrets or tenant material. [S13, S18]

## Remaining decisions and experiments

No experiments were executed. High-value future acceptance questions are:

1. With outbound access denied, do clean bootstrap, normal operation, node replacement, upgrade and restore all succeed from the declared artifact inventory? Which optional extensions fetch undeclared dependencies?
2. What effective Ambari/Bigtop service coverage and supported upgrade paths match the required catalog, and which lifecycle adapters remain absent? Can mutable snapshot inputs be replaced by reproducible, provenance-checked inputs?
3. Which management-runtime/service-deployment/scheduler combination and OS/JDK/Python/Kubernetes versions will humans select for certification? Can controllers coexist without conflicting ownership?
4. Can a failed stateful upgrade recover at each failure boundary, including restoration of keys, management state and application consistency? What RPO/RTO and rollback exclusions will the product promise?
5. Do mirrored signatures, scanner databases, plugins and offline identity/secret flows work without public infrastructure? What licensing/source-delivery obligations apply to the actual redistributable?

Reusable foundations reduce packaging, reconciliation, storage and telemetry work. Remaining product work is certification, dependency manifests, service-specific lifecycle/recovery contracts, unified health/configuration semantics and diagnostics. Release planning should express those capabilities and acceptance evidence, not dates or arbitrary upstream mixtures.
